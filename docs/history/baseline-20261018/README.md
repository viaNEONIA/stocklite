## v10.1.1 修正内容

ユーザー報告「D/Eが処理に失敗して強制終了」に対応。

添付v10.1ログではD/html5はnot-found-or-error、D/ZXingは38msで一致。E/fullは51msで一致、E/live-regionはnot-found-or-error。したがって、D/Eが全く実行不能ではなく、一部は解析完了している。旧版は撮影後の仕様としてカメラを停止していた。入力未完了やA計測中などの事前条件エラーも一般的なエラーメッセージへまとめてカメラを停止し、原因を記録していなかった。これらが報告された全事象を説明するとは断定しない。Safari自体が終了したかどうかはJSONから分からない。

- D/Eは撮影後もカメラを維持する。カメラ用の解析のみpause(false)で一時停止、ファイル用は別Html5Qrcodeインスタンスで実行し、finallyでresumeする。
- 期待コード未入力・不正、A計測中、映像未準備は理由を個別表示し、カメラを停止しない。
- 読取不成立とAPI例外を分離。画面と記録JSONのerrorsに失敗段階・固定コードを残す。期待コード・認識コード・生の例外メッセージは出力しない。
- D/Eの途中で画面が非表示になった場合は、解析完了後にカメラを停止する。読み取り不成立は比較処理の終了として扱い、アプリ異常終了と区別する。
- 模擬試験で、比較後のカメラ維持、不正期待値での復帰、API例外後の復帰、例外メッセージの非出力を追加検証。

使用: 同じ試験用ホストのファイル一式をこの版へ置き換え、再読み込み。書き出したJSONのbuildがv10.1.1-dev-recovery-1になることを確認する。本体へ上書きしない。期待JANを入力、カメラ起動、Aを開始せず直接D/Eを実行できる。D/Eの不成立は診断欄にnot-found、API例外はerrorとコードを表示する。カメラを毎回起動し直す必要はない。

Dの解釈: 同じPNG・EAN-8/EAN-13/QRを両経路へ渡す。ただしhtml5-qrcodeのscanFile内部は独自canvas/余白処理とrobust decodeを行うため、内部入力画素が同じとは言わない。結果の差は「公開ファイル解析経路の差」であり、デコーダ本体だけの差とは断定しない。内部canvas寸法を確実に取得できないため、Dには入力PNG寸法を記録する。

Eの解釈: 全体で一致しライブ領域で不成立なら、同じエンジンでも切り出し・縮小が不利な条件。両方一致なら、Aのデコーダ経路・タイミング・フリップ試行などを追加調査する。全体で不成立なら、フレーム品質や姿勢も引き続き候補。

D/Eは画像を1回だけ取得し、撮影・PNG化時間と各解析時間を分ける。合計は各解析に共通準備時間を加えた値で、二つのエンジンの同時解析速度や連続スキャン性能を表さない。JAN照合は厳密な桁数で行い、UPC等の別形式との同値扱いは行わない。v10.1.1では読取不成立（not-found）とAPI例外（error）を分ける。判断できない例外はerrorとし、エラーコードと処理段階だけを記録する。

## 確認した結論

**写真とiOSライブではデコーダが異なる。写真が安定することだけで、ライブの画質が原因とは確定できない。**

| 経路 | 実際の処理 |
|---|---|
| iOSライブ | html5-qrcode 2.3.8 → EAN-8/EAN-13/QR指定、ネイティブBarcodeDetector無効 → 成功callback → handleCode |
| 写真 | File → Object URL → Image.decode → 自然寸法canvas（明示的縮小なし）→ PNG Data URL → ZXing 0.21.3 BrowserMultiFormatReader.decodeFromImageUrl → handleCode |
| Androidライブ | getUserMedia → BarcodeDetectorが全3形式対応なら採用 → それ以外はZXing連続読取 |
| 今回のC | html5-qrcodeで起動したvideo → ライブ解析を一時停止 → Bと同じcanvas/PNG/ZXing入口 → 再開 |

写真に明示的な回転補正処理はない。ブラウザの画像デコードに依存する。写真のZXingは既定の形式集合であり、ライブと認識形式の指定も異なる。今回も元の写真経路を再現し、形式指定は勝手に統一しない。

B/Cは同じ画像解析関数を使う。A/Cはエンジンだけでなく切り出し範囲・入力サイズも異なる。Cが速くても「エンジンが原因」と単独では判定しない。

## 実機試験手順

まず条件「v9既定」でJAN-13、JAN-8を各10回、QRも退行比較用に10回実施する。各回の印刷物・照明・距離・角度・背景を固定する。

- A: バーコードを一旦外してカメラ起動。起動完了後、A開始ボタンを押して直ちに枠へ入れる。ボタンから成功までを計測し、10秒でタイムアウト。人の操作遅延を含むので同じ操作をそろえる。
- B: iPhone標準カメラで同じ印刷物を撮影し、写真入力へ渡す。カメラは停止する。画像デコード・canvas/PNG変換・ZXing解析の総時間と、変換・解析時間を記録。写真撮影・ファイル選択の所要時間は含まれないため別途手記する。
- C: 同じカメラを起動して印刷物を静止。Cを押すとそのvideoのフレームをBと同じ入口で解析。解析中のライブ検出は一時停止する。元映像からフルフレームを取得する。
- 各成功結果は印刷物と照合し「一致」または「誤認識」を押す。次の試行前に必ず判定する。未照合は成功率へ数えない。
- A→B→C、B→C→A、C→A→Bと順番を交替し、条件間の順序偏りを減らす。Bでカメラが停止するためA/C前には再起動する。
- JSONを書き出す。ページ更新でメモリ上の記録は消える。

A/B/C既定比較後、AFのみ・ズームのみ・解像度のみ・15fpsのみ・横長領域のみをそれぞれA/Cで測る。条件変更時には一旦停止し、再起動して既定から設定する。非対応条件は処理失敗となるため、その条件は欠測として記録し、既定へ戻す。設定要求値と実際のsettingsを区別する。

判定目標はJAN-8/JAN-13別に一致分中央値3秒以内、10秒以内一致率90%以上、誤認識0。失敗・中断もJSONに残る。画面の率は中断を除いた試行を分母にし、中断は別表示する。異なるモード・形式・条件を混ぜて集計しない。

Cが速くAが遅いならライブの切り出し・解析経路を重点調査。Bが速くCが遅いなら映像の画質・解像度および変換差を重点調査。いずれも原因確定ではない。
