# StockLite v10.4.2-dev iPhone統合試験版



## v10.4.2 一時停止UIの準備待ち

ユーザー画像のエラーは `[internal error] scanner paused UI element not found`。BUILDはv10.4.1、処理段階は起動失敗：読み取り中、APIの開始完了は返っていた。従ってカメラ開始後のhtml5-qrcode.pause(false)で失敗し、後片付けでカメラを閉じたケースと判断する。

html5-qrcode 2.3.8ソースではstartのPromiseを解決する経路と、onRenderSurfaceReadyからsetupUiを呼んで一時停止UIを生成する経路が分かれている。pauseは状態をPAUSEDへ遷移させた後でUI表示を行い、UIが未生成なら今回のエラーを投げる。単に例外を無視して続行すると不完全な状態を残し得るため、その回避は行わない。

変更: start完了後、videoの実寸が正で解析canvasも生成済みになるまで25ms間隔で待機し、その後にpause(false)する。setupUiはcanvas追加から一時停止UI生成まで同じ同期処理内で行うため、canvasを確認した次の非同期処理でpauseする。ライブラリの非公開フィールドは参照・変更しない。8秒で準備できなければCameraSurfaceTimeoutを表示。停止・画面遷移・再起動でセッションが変われば待機を中止し、遅れてpauseやZXing開始を実行しない。

配置: ZIP内ios-candidateの一式を試験環境へ配置し、stocklite-v10-4-2.htmlを開く。ヘッダーはv10.4.2-dev、診断BUILDはv10.4.2-dev-surface-ready-1。過去版の固有名HTMLは変更履歴用で、今回の起動には使用しない。

検証: 準備前はwaitIOSSurfaceが解決しないこと、映像/canvasが揃った後に解決すること、セッション変更時は中止することを模擬試験で確認。数量保存・従来方式への切替などの既存模擬試験も合格。iPhone実機での修正後動作は未確認。

参照した固定版ソース: https://github.com/mebjas/html5-qrcode/blob/v2.3.8/src/html5-qrcode.ts のstart、setupUi、pause、showPausedState。

以下は過去版の記録。今回の確認文字列はv10.4.2-dev-surface-ready-1。

## v10.4.1 カメラ起動修正

ZXing方式でカメラが起動しない報告に対応。実機の根本原因は未確定だが、次の不具合を修正した。

- カメラより先にZXing取得を待っていた順序を、診断版と同じ「html5でカメラ起動→html5解析をpause(false)→ZXing準備」に変更。ライブラリの取得中はその段階を画面に表示する。
- v9からの既存コードにあったclear().catch(...)を削除。clear()は同期APIのため、例外時の後片付けで新しいTypeErrorを起こし、元の起動エラーを隠し得た。awaitは同期戻り値にも使えるが、戻り値への.catch呼び出しはできない。
- TypeErrorを一律にHTTPS不足と説明していた表示を修正。HTTPS判定はInsecureContextErrorとし、その他は実際の例外名・メッセージを表示。
- 失敗段階とエラーをカメラ診断欄へ表示し、自動で欄を開く。カメラ再起動ボタンを追加。html5ライブラリ取得に12秒のタイムアウトを追加。
- 読取方式・連続2回一致・数量確定・データ形式は維持。共通のエラー説明はAndroidにも適用されるが、Androidのスキャナ選択/解析分岐は変更していない。

配置: ZIP内ios-candidateのファイル一式を試験環境へ配置し、stocklite-v10-4-1.htmlを開く。ヘッダーがv10.4.1-devであることを確認。名前を固定したindex.htmlでも起動できるが、旧版との取り違えを避けるため固有名の起動ファイルも同梱した。カメラ起動に失敗した場合は、画面の【失敗段階】と診断欄に理由が残る。従来方式への切り替えも可能。

模擬試験追加: clearがundefinedを返しても元のカメラ開始エラーが維持されること、カメラ起動/一時停止後にZXingをロードすること、ライブラリ取得失敗で例外が伝わること、TypeErrorがHTTPS不足と誤表示されないことを確認。実機での修正後起動は未確認。

以下は共通仕様と初版の記録。今回の確認文字列はv10.4.1-dev-camera-start-1。

採用する暫定方式: ZXing 0.21.3で全体映像をPNGとして順次解析し、異なる映像フレームで有効な同一コードを連続2回、1秒以内の間隔で確認する。解析間隔は最短200ms。カメラ取得は実機試験で使ったhtml5-qrcode 2.3.8を維持し、その解析を一時停止してZXingで認識する。

これは在庫アプリ本体へ組み込んだ隔離試験版。診断版のFボタン、期待JAN入力、3秒カウントダウンはない。スキャン画面へ入ると読取を開始し、登録済みなら数量確認、未登録なら既存の品目登録へ進む。数量の変更は「確定」ボタンで保存する。

## 使用手順

1. 本番の設定画面でJSONバックアップを手動出力し、保管する。この作業では本番端末のバックアップ取得は実施していない。
2. ZIPのios-candidate内を、本番と異なるオリジンのHTTPS試験サイトへ配置。単なる同一GitHub Pagesの別パスや、同じユーザーの別リポジトリは通常オリジンが同じなので隔離にならない。本番のindex.htmlへ上書きしない。
3. 初回はオンラインでSafariから開き、ヘッダーのv10.4-dev表示を確認する。解析ライブラリは外部CDNから取得する。初回通信が失敗した場合は通信を確認し再起動するか、従来方式へ切り替える。
4. 空の試験データで登録・スキャン・数量確定を確認する。必要なら試験サイトだけに本番JSONのコピーを読み込む。本番データの編集結果とは独立しているため、試験用JSONを本番へ復元しない。
5. スキャン画面でコード全体と余白を映像内に入れる。iPhoneはZXing全体映像が既定。読み取り方式で「従来方式」を選ぶとv9 html5-qrcodeへ戻せる。端末の保存データ形式は変わらない。
6. PWAは試験サイトをホーム画面へ追加して動作を確認する。サイトデータを消す必要はない。

## 実装・保護

- 基準ソースはGit履歴上のv9 BUILDを持つ55131b3。v9 ZIPとのバイト一致は未確認。
- iPhone分岐だけを新方式へ接続。Androidのスキャナ分岐はv9と同一。
- JAN-8/JAN-13は形式、桁数、チェックデジットを検査。QRはZXingの形式情報に基づいて受け付け、JANチェックをしない。
- 数量確認・購入・使用・品目登録・バックアップ・復元・IndexedDBの関数はv9と同一。DBはstocklite v1 / state / data。初期化やマイグレーションを追加していない。
- 数量確認中は追加の画像解析を休止。同じコードが映り続ける場合の再通知を抑え、読取不可4フレームまたは別コードへの移行で再読取できる。1800msの既存重複抑制も維持。
- 解析は常に1件ずつ。停止時は遅延結果を破棄し、再起動時は前の解析の終了を待つ。画面非表示・pagehideでiPhoneカメラも停止。
- 試験用SWはstocklite-ios-candidateプレフィックスのキャッシュだけを整理する。本番キャッシュは削除しない。外部CDNライブラリのオフライン利用は保証しない。
- 認識コード・カメラ画像を診断ログとして保存しない。品目のコードと在庫履歴は既存アプリ機能として保存される。
- ios-fullframe.jsの内容はindex.html内にも埋め込み済み。実行時に別JSの配置を忘れて起動できなくなる問題を避ける。

## 必要な受入確認

Safariとホーム画面PWAでJAN-13/JAN-8/QRを確認。登録済みの購入・使用は確定前に在庫不変、確定後に1回だけ保存されること。未登録コードは登録画面へ進むこと。読取途中の画面切替、数量確認のキャンセル、権限拒否・復帰、再起動後の保存状態を確認。Androidは既存速度と全機能の回帰を確認する。

初回認識速度はv10.3診断版の統一手順で別途比較する。本体では操作者がコードを映像へ入れた瞬間を自動計測しない。速度目標の達成は未確定。
